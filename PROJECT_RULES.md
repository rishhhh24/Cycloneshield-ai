# CycloneShield AI - Engineering & Development Rules

## 1. Core Engineering Principles

1. **Keep it Simple & Modular**:
   - Avoid overengineering or premature microservice splitting. Maintain a single, clean Flask backend and a clean Vanilla JS frontend.
   - Component boundaries must be strictly respected (`services/` for business/GIS logic, `api/` for Flask HTTP routing, `models/` for numerical models).

2. **No Framework Overkill**:
   - Do NOT introduce React, Vue, Angular, or heavy frontend bundlers (Webpack/Vite) unless explicitly instructed by the Lead Architect. Vanilla JS + HTML5 + Tailwind CSS is mandatory for MVP speed and transparency.

3. **Never Delete Working Code Unnecessarily**:
   - Preserve existing utility functions, model definitions, and API routes when adding features or refactoring.

---

## 2. Strict AI Boundary & Non-Fabrication Rules

1. **Numerical Risk Authority**:
   - All numerical scores (0–100), hazard breakdowns, distance figures, exposed asset counts, and flood depth estimations MUST be generated by the Python GIS/ML Risk Engine (`risk_engine.py`).

2. **Generative AI Role**:
   - Google Gemini AI (via `google-genai` SDK) is strictly restricted to:
     - Narrative explanation of calculated risk factors.
     - Natural language answer generation for disaster commanders.
     - Scenario outcome reasoning.
     - Pre-landfall emergency advisory creation.

3. **Non-Fabrication Policy**:
   - **Gemini AI MUST NEVER fabricate, hallucinate, or alter any numerical risk score.**
   - All prompts passed to Gemini must supply the calculated numerical payload in JSON context.
   - If a requested metric is missing from the payload, Gemini must state that the data is unavailable rather than making up a value.

---

## 3. Key Management & Environment Security

1. **Zero Hardcoded Secrets Policy**:
   - NEVER commit API keys, secret tokens, or private configuration to Git repositories.
   - Use `python-dotenv` in backend Python files.

2. **Environment File Standard**:
   - Maintain `.env.example` with sanitized placeholder keys.
   - Developer `.env` files must remain strictly listed in `.gitignore`.

---

## 4. Data Transparency & Labeling Policy

1. **No Data Fabrication Claim**:
   - Do NOT claim that demo or simulated track data represents live real-time NOAA or IMD feeds unless connected to authenticated real-time APIs.
   - All sample track data must carry `"is_demo": true` metadata.

2. **UI Data Badging**:
   - Front-end headers and cards displaying sample data must clearly show a **`DEMO DATA`** or **`SIMULATION`** badge.

3. **Nomenclature Policy**:
   - The primary risk metric output must ALWAYS be referred to as **"Infrastructure Vulnerability Risk Score"** (scaled 0 to 100).
   - Do NOT claim "Exact Physical Destruction Prediction". Frame outputs as vulnerability risk indices and exposure decision support.

---

## 5. Coding Standards & Error Handling

1. **Defensive API Calls**:
   - All backend API endpoints must catch exceptions gracefully and return standardized JSON error objects (`{ "success": false, "error": { "code": "...", "message": "..." } }`).

2. **Client Loading & Error States**:
   - Frontend components must display visible visual loading spinners/skeletons during API fetches and render informative error alerts if an API call fails.

3. **Python Typing & Docstrings**:
   - Write clear docstrings for every service function.
   - Use standard type hints (`str`, `int`, `float`, `Dict`, `List`, `Optional`) in python signatures.
